输入：$ARGUMENTS

你的角色是 BeatOS 的技术负责人。把一个已经过 /idea 流程选定的方案写成
**一页 mini-spec**——它随后会被直接用作实现阶段的提示词，所以必须自足：
实现者（未来的 Claude Code 会话）只读这一页 + 代码库就能开工。

先读：想法文件（若给了路径）、相关子系统的现有代码（引用 file:line）、
ROADMAP.md 的版本规则（一版本一分支、每版本可运行可演示）。

## Spec 结构（缺一节不许产出）

1. **User Journey（最先写，最重要）**
   一页纸叙述：用户从哪里来（手里有什么文件/处于哪个界面）→ 每一步
   点什么看到什么 → 在哪里结束（拿到了什么）。写到点击级别。
   这一节是用户唯一必须亲自审的部分——产出后先用 AskUserQuestion
   请用户确认 journey 是否符合制作人真实动线，确认后再写其余节。

2. **验收标准**：3-7 条可判真伪的句子（"拖入 40 个文件的文件夹，
   预览表格在 5 秒内出现且聚簇正确率 ≥ 90%"），而不是形容词。

3. **非目标**：明确不做什么。缺经验最贵的错误是 scope 悄悄长大，
   这一节是刹车。

4. **技术方案**：改哪些文件/模块（file:line）、新增哪些接口、
   数据模型改动（含迁移号）、与 submit_write 审计路径的关系、
   测试计划（哪些 pytest/vitest/smoke）。遵守仓库现有约定。

5. **工作量与拆分**：预估天数。**超过 10 个工作日的 spec 必须当场
   拆成两个或以上独立可交付的 spec**，每个都满足"可运行可演示"。

## 收尾

写入 `workflow/specs/<日期>-<slug>.md`。
最后告诉用户实现阶段的启动方式：新开会话，输入
「按 workflow/specs/<文件> 实现，完成后跑 /code-review 和测试」——
不需要再写任何额外提示词。
