# BeatOS AI 协作开发流程（2026-07）

> 目标：把「懂痛点但缺经验的独立开发者」和「有经验但不了解你真实处境的 AI」
> 的分工结构化，让双方都只做自己擅长的事。
> 背景分析见 [PRODUCT-ANALYSIS-2026-07.md](../PRODUCT-ANALYSIS-2026-07.md) 与
> [SOLUTION-DESIGN-REVIEW-2026-07.md](../SOLUTION-DESIGN-REVIEW-2026-07.md)。

## 核心原则：分工按"谁拥有事实"划分，而不是按"谁聪明"

| 你独有、AI 没有的 | AI 有、你暂时缺的 |
|---|---|
| 真实痛点（你是制作人） | 方案空间与行业先例 |
| 用户反馈的第一手原话 | 工程权衡（何时该简单、何时该稳） |
| 价值判断（这个体验对不对味） | 实现能力与自审能力 |
| 验收（真实走一遍工作流） | 对"伪需求"的免疫力 |

由此推出三条铁律，贯穿所有环节：

1. **你不写方案，你回答问题。** 你的提示词质量有限——所以反转方向：
   由 AI 按固定模板访谈你，把模糊想法榨成结构化的 Problem Brief。
   你从"写 prompt 的人"变成"被采访的领域专家"，这是你能提供的最高质量输入。
2. **AI 必须先挑战、再服从。** 任何想法进入实现之前，AI 必须先给出
   "反对做这件事的最强理由"和"一个更简单的替代"。你只做选择题。
   这防止 AI 盲从你的经验盲区，也防止你盲从 AI 的第一反应。
3. **所有决策落纸。** 每个选择记入 decision log 一行。未来任何 AI 会话
   都能读到"当时为什么这么定"，杜绝反复重开已决策的问题——
   这是独立开发者最大的隐性时间黑洞。

## 主管线：模糊想法 → 高质量落地

```
[随手记]  ideas/inbox.md 一句话即可，零门槛，不许自我审查
    │
[/idea]   AI 访谈你(≤5问) → Problem Brief → 3方案(推荐/更简/反对) → 你选
    │
[/spec]   选定方案 → 一页 mini-spec (user journey + 验收标准 + 非目标)
    │        你只审一件事：journey 是否符合制作人的真实动线
    │
[实现]     Claude Code 按 spec 干活 —— spec 就是提示词，不需要你再写
    │
[验收]     AI 跑 /code-review + verify；你做的不是看代码，
    │        是「真实走一遍 journey」—— 这是你的验收，别人替不了
    │
[/retro]  决策与教训回流 decision log / feedback log
```

关键机制说明：

- **想法收集箱（ideas/inbox.md）**：想法出现的那一刻不需要质量，只需要
  被记下。每周挑一条跑 `/idea`。垃圾想法会死在访谈环节——死得越早越便宜。
- **`/idea` 的三方案强制格式**是整个流程的心脏：
  ① 推荐方案（AI 的专业判断+理由）② 明显更简单的方案（对抗过度工程）
  ③ 不做的最强理由（对抗伪需求）。你见到的永远是权衡后的选择题，
  而不是需要你有经验才能评估的开放题。
- **spec 即提示词**：实现阶段直接引用 spec 文件，你不再手写指挥。
  spec 有硬约束：预估超过两周的必须拆小（大 spec 是缺经验时最贵的错误）。
- **验收分层**：代码正确性归 AI（自动审查+测试），体验正确性归你
  （走 journey）。你看不懂 diff 没关系——你看得懂"这个流程顺不顺"，
  而那才是唯一重要的验收。

## 反馈回路：内测数据 → 开发方向

**记录（你，随时）**：反馈进 `memory/feedback-log.md`（模板见
[templates/feedback-log.md](templates/feedback-log.md)；repo 是公开的，
真实日志放本地私有的 `memory/`，用户用匿名编号）。
唯一重要的纪律：**记原话，不记你的翻译**。
"导入好麻烦"和"要是能整个文件夹拖进来就好了"是两条不同的数据——
缺经验的人最容易犯的错就是把用户的话提前翻译成自己想听的结论。

**分析（AI，双周）**：跑 `/triage` —— 聚类原话 → 按 频次×严重度 排序 →
对照 ROADMAP 找出"用户在喊但 roadmap 没有"和"roadmap 有但没人喊"的差集 →
输出下个迭代建议。你依旧只做选择题。

**回顾（AI，每月）**：跑 `/retro` —— 读 changelog + git log + 反馈日志，
做三件事：bug 聚类（bug 的分布就是设计弱点的地图）、时间分配审计
（工程 vs 分发是否守住了 30/70）、苛刻的 PM 拷问（本月接触了几个真实用户？）。

## 安装与目录

```bash
# 把命令装进本地 Claude Code（.claude/ 是 gitignore 的本地目录）
mkdir -p .claude/commands && cp workflow/commands/*.md .claude/commands/

# 初始化本地私有的反馈/决策日志
mkdir -p memory && cp workflow/templates/feedback-log.md memory/
cp workflow/templates/decision-log.md memory/
```

| 路径 | 是否入库 | 用途 |
|---|---|---|
| `workflow/` | ✅ 公开 | 流程文档、命令源文件、模板 |
| `workflow/ideas/` | ✅ 公开 | inbox + 每个想法的 Brief/方案记录 |
| `workflow/specs/` | ✅ 公开 | 已批准的 mini-spec |
| `memory/feedback-log.md` | ❌ 本地 | 真实用户反馈（含个人信息） |
| `memory/decision-log.md` | ❌ 本地 | 决策日志（AI 每次会话可读） |

## 节奏（把"经验"变成日历事件）

- **每天**：想法进 inbox（10 秒），反馈进 log（1 分钟）。
- **每周**：跑一次 `/idea` 消化 inbox 里最有感觉的一条；工程时间只花在
  有 spec 的事上。
- **双周**：`/triage`，定下个迭代。
- **每月**：`/retro`，并回答它最后的三个拷问。

## 为什么这套流程针对"缺经验"有效

经验的本质是两样东西：**见过足够多的方案空间**（知道有哪些选择）和
**被现实反馈打过足够多次**（知道哪些选择会痛）。这套流程把前者外包给
AI（三方案强制格式让你每周都在看方案空间），把后者压缩进双周反馈回路
（真实用户的原话按频次排序，就是现实在打你，只是打得快、打得便宜）。
你不是在绕过经验积累——你是在把十年的经验积累压进两年，
且每一步都有纸面记录可复盘。
